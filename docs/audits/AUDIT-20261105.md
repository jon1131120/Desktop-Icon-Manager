## 二、P0 级（必须修，直接影响可用性）

### P0-1 同步永不收敛：应用后被 QSpace 重排误判为"用户改动"

**证据链**（中枢 + 三台日志实测）：
```
01:02:54  MBP    上报 4084cd33     ← 用户拖图标（正常）
01:03:43  Studio 上报 2e9b70af     ← 无人操作 Studio，它把"应用后的重排结果"当自己改的
01:04:29  Air    上报 568765a4     ← 同上
01:05:14  MBP    应用 Air 布局 → moved=31   ← 用户布局被冲掉
```

**根因**（两处叠加）：
- `main.swift:131` `atomicWriteConfAndRestartQSpace`：重启 QSpace 后只 `Thread.sleep(0.6)` 就返回，
  QSpace 尚未完成图标重排 → 此时读到的指纹是"半成品"
- `applyRemote` 末尾把"应用后立即读到的指纹"记为 baseline → 之后 QSpace 排完盘 → 指纹变化
  → `broadcastIfNeeded` 判定"用户改了布局" → 上报 → 覆盖中枢 → 其他机器应用 → 再次重排 → **无限循环**

**修复**：
1. 应用后设置 **60 秒吸收期**（`suppressBroadcastUntil`），期内**持续把当前指纹写回 baseline**，不上报
2. 重启 QSpace 后**轮询指纹直到连续 2 次相同**（最多 10 秒）再记 baseline

### P0-2 外接屏右手边图标重叠 + 歪斜（用户实测）

**实测数据**（当前合盖单外接 C 套，2560×1410，lod=96，列距 113）：
```
col=22: x=2505 有 6 个, x=2493 有 2 个     ← 同列两种 x，偏 12px（歪）
col=21: x=2415 有 7 个, x=2380 有 2 个     ← 偏 35px（歪）
行2/3/4/5/6/9: 最小间距 90px < 列距 113    ← 90 是 B 套列距，混套残留（重叠）
DeepSeek谷峰定价监控 x=75                  ← 落在组件区（x0=120 左侧）
```

**根因**（`main.swift:812` 附近）：
```swift
if ox >= 0 && oc == dc && orow == dr {
    ni["x"] = ox; ni["y"] = oy        // 格号相同就原地保留像素
}
```
- 只要"反推出的格号"与"目标格"相同，就**保留原始像素**，哪怕它是 2505（标准值 2493）、
  或是 B 套遗留的 90px 间距 → **脏坐标永久固化**
- 从 B 套切到 C 套时，B 套间距 90 < C 套图标宽 96 → **图标互相压 6px** = 视觉重叠

**修复**：
1. `oc == dc && orow == dr` **且** `abs(ox - 标准x) <= 3 && abs(oy - 标准y) <= 3` 才原地保留
2. 否则一律写标准格位坐标（`x0 + (col-1)*step`）
3. 越界图标（`x > 屏宽 - lod`）向左挪一列

## 三、P1 级（高，尽快修）

### P1-1 切套判定：精确尺寸匹配 + 双屏误判
```swift
func specForSize(_ w: Int, _ h: Int) -> GridSpec? {
    if w == 1710 && h == 1073 { return SPEC_A }   // 精确相等
    if w == 1728 && h == 1084 { return SPEC_B }

// 兜底：default: (hasBuiltin && NSScreen.screens.count == 1) ? SPEC_B : SPEC_C
```

1. **`!used.contains` 补丁未落盘**：第一次"修复"后仍重叠。是三台自动验证脚本（`/tmp/check.py`）抓出来的 —— 证明**必须有独立于被测代码的验证手段**，靠 app 自己的 verify 会漏（app verify 当时也报 bad，但修复没生效）。定位手法：加 `--applydebug` 打印每个图标的 `oc/dc/usedHas` 分支，一眼看出 6 个图标 `usedHas=true` 却 `moved=0`。

# 九、P0-4 撤回声明（2026-11-05 02:00）

**P0-4「三套列数超出屏幕物理宽度」是我的误判，已撤回。**

- **错误**：把 `x` 当作图标**左边缘**，按 `x + lod <= 屏宽` 判断越界
- **事实**：QSpace 的 `x/y` 是图标**中心点**。A 套第 21 列 x=1660 → 1660+32=1692 < 1710，**不越界**
- **我的错误处理**：① 把列数减到 A20/B18/C21（用户布局在第 21/19/22 列的图标被 clamp）
  ② 叠加"越界左移"逻辑，把合法的 C 套第 22 列(x=2493)左移到 21 列 → 与原本 21 列的图标**撞车**
  ③ 结果：用户手动布局被**连锁推移 39 个图标**，表现为"几台都是重叠的"
- **修正**：列数恢复 21/19/22；`inBounds` 与越界左移改用 `lod/2`；selftest 恢复全量
- **恢复**：用用户手动快照 `[Air] 内置屏-261104.json` 作真源重新下发，三台 PASS，
  42 个原快照图标位置逐个比对**全部正确映射**

**教训**：判断"越界"前必须先确认坐标系语义（左上角 / 中心点 / 基线）。三套参数是用户逐格标定的，
在没有确凿证据前**不应改动标定值**——应当先问，而不是先改。
