## 五、反复出现的坑（元教训）

### 1. 每修一个机制，就要查它的失效边界
- 加"重推"（第八轮）→ 漏了"时钟落后"（第九轮）→ 补 `clockOffset` → 又漏了"超前兜底不更新"（第十轮）
- **模式**：机制 A 假设条件 X，条件 X 不成立时静默失效。每次加机制必须列出它的前置假设并逐个证伪。

### 2. 我改代码引入的 bug 比原始设计的 bug 多
十轮 80 项里，第 6~10 轮的发现**几乎全是前一轮改代码引入的**：
假开关（语法残留）、`skipPullOnce` 残留、`clockOffset` 兜底漏洞、`MAX_COORD` 未定义。
**原始核心链路（映射/快照/应用/校验）十轮一次都没坏过。**

→ 结论：系统已进入「改动风险 > 设计缺陷」阶段，每次改完跑 15 条主链回归比开新维度更有价值。

### 3. 检查"某物是否已存在"不能搜整个文件
注释、字符串、UI 文案都会误命中。要用锚定模式（`^NAME\s*=`）或结构化判断。

### 4. 给用户看的编号 / 显示的路径 必须和实际取对象共用同一份逻辑
两套规则 = 不报错的错位。表现是"我明明选了 A 却回滚到 B"。

### 5. 测试必须用过去的时间戳
`syncAt = now + 9` 会让正常请求被接受 → 污染中枢真源。用 `now - 1000` 走拒绝路径。

### 6. 一次性标记要在每条提前 return 的路径都清
`if flag { flag=false; return }` 只清了一处，另一处 `guard return` 就漏。

### 7. 文档里的"收敛值"会过时，唯一真源是代码
记忆/README 写 20/18/21，代码实际 21/19/22。**改代码后要 grep 文档**。
